# 07. Нагрузка, отказоустойчивость, безопасность

> Принцип: **сначала правильная форма, потом масштаб**. Сейчас всё локально (Docker Compose). Код пишется так, чтобы потом без переписывания переехать на сервер и масштабироваться. Цифры ниже это цели, которые нужно проверять нагрузочными тестами (k6), а не обещания.

## 1. Ключевые идеи высоконагруженного дизайна

1. **Stateless API.** В процессе бэкенда нет состояния (сессии в БД/Redis, файлы в объектном хранилище). Тогда можно запускать N копий за балансировщиком.
2. **Тяжёлое делаем асинхронно.** Рендер DOCX/PDF и ИИ-запросы самые дорогие операции. Они идут через очередь и пул воркеров, а не в HTTP-обработчике.
3. **Кэшируем всё, что общее.** Каталог шаблонов, страницы шаблонов, статика: через CDN/кэш. База нужна для личных данных.
4. **Ограничиваем всё.** Rate limit, квоты, таймауты, размеры загрузок, потолки токенов. Бесплатный сервис без лимитов это уязвимость и счёт за ИИ.
5. **Деградируем красиво.** Если ИИ упал, конструктор работает. Если PDF-воркер перегружен, DOCX всё равно скачивается.

## 2. Технологии (выбор и почему)

| Слой | Выбор | Почему / альтернатива |
|---|---|---|
| Бэкенд | **Go** (chi, pgx, sqlc) | быстрый, мало памяти, горутины под много соединений; вы им владеете |
| Фронтенд | **Next.js + TypeScript**, SSR/ISR для каталога | SEO важен (люди ищут «договор аренды образец»), страницы шаблонов кэшируются |
| БД | **PostgreSQL 16** + **PgBouncer** | надёжность, JSONB для анкет, pgvector для норм; PgBouncer держит много клиентов |
| Кэш, лимиты, сессии | **Redis** (позже Valkey/кластер) | rate limit, счётчики ИИ, кэш |
| Очередь | **NATS JetStream** или Redis Streams (на старте проще: Postgres + `river`/`asynq` на Redis) | рендер и ИИ-задачи, повторы, dead-letter |
| Файлы | **S3-совместимое** (MinIO локально, Yandex Object Storage / Selectel в проде) | DOCX/PDF, загрузки; не на диске сервера |
| Рендер PDF | воркер с LibreOffice headless в **отдельном контейнере**, лимиты CPU/RAM | изоляция, т.к. процесс тяжёлый и парсит недоверенные файлы |
| Прокси/балансировщик | **Traefik или Nginx**, TLS | маршрутизация, HTTP/2, сжатие, лимиты |
| Edge | **CDN + WAF** (Cloudflare недоступен/ограничен в РФ, смотреть Yandex Cloud CDN / Selectel / DDoS-Guard / Qrator) | выбрать РФ-провайдера |
| Оркестрация | Docker Compose → **k3s/Kubernetes** (или Nomad) на этапе масштабирования | сразу Kubernetes не нужен |
| Наблюдаемость | **OpenTelemetry**, Prometheus, Grafana, Loki, Alertmanager; Sentry | видеть узкие места до падения |
| CI/CD | GitHub Actions: тесты, линтеры, сканеры, сборка образов, деплой | |

## 3. Три стадии инфраструктуры

### Стадия L. Локально (сейчас)
Docker Compose: `web`, `api`, `worker`, `postgres`, `redis`, `minio`, `pgbouncer` (опционально), `mailpit` (почта). `make dev` поднимает всё. Нагрузочные тесты k6 можно гонять уже здесь.

### Стадия S. Один сервер (первый запуск)
VPS/выделенный сервер в РФ, Docker Compose или k3s, Traefik + TLS (Let's Encrypt), автобэкапы Postgres (pgBackRest/WAL-архив) и объектного хранилища, мониторинг, firewall, fail2ban/CrowdSec, обновления по расписанию. Одна точка отказа: это осознанный компромисс.

### Стадия H. Отказоустойчивая
- 2-3 узла приложения в разных зонах, балансировщик с health-check.
- Postgres с репликой и автоматическим фейловером (Patroni) или управляемая БД провайдера; чтение каталога с реплики.
- Redis с Sentinel/кластером. Очередь с репликацией.
- Воркеры рендера и ИИ масштабируются отдельно (по длине очереди).
- Blue/green или rolling-деплой без простоя, миграции БД обратно совместимы.
- Цели: доступность 99.9%, RPO ≤ 5 мин, RTO ≤ 30 мин (проверять учениями восстановления, раз в квартал).

## 4. Ориентиры по производительности (проверяются k6)
- Каталог/страницы шаблонов из кэша: p95 < 200 мс при тысячах запросов в секунду.
- Сохранение анкеты: p95 < 300 мс.
- Рендер DOCX: p95 < 3 с, PDF: p95 < 8 с, очередь выдерживает всплески (пользователь видит прогресс).
- ИИ-чат: первый токен < 2 с (стриминг).
- Правило: узкое место ищем профилированием и метриками, не угадыванием.

## 5. Безопасность

**Приложение (опираться на OWASP ASVS и Top 10):**
- Пароли: argon2id. Сессии: httpOnly + Secure + SameSite cookie, ротация, выход со всех устройств. Опционально 2FA (TOTP) и вход через Яндекс ID.
- CSRF-защита, строгая CSP, HSTS, безопасные заголовки, валидация на сервере (все входы), параметризованные запросы (sqlc).
- Авторизация на уровне объекта: каждый запрос проверяет, что документ/карточка принадлежит пользователю (тесты на IDOR обязательны).
- Rate limit на вход/регистрацию/ИИ, защита от перебора и ботов (капча на подозрительном поведении), подтверждение email.
- Загрузки (проверка договора): лимит размера, проверка типа по содержимому, антивирус (ClamAV), парсинг в изолированном воркере без сети.
- Рендер шаблонов: экранирование данных пользователя, никакого исполнения кода из шаблонов.

**ИИ:**
- Ключ только на сервере. Квоты на пользователя в сутки и общий потолок расходов в месяц (при остановке по потолку чат отключается, остальное работает).
- Защита от prompt injection: загруженные тексты это данные; ответ модели парсится как структура; у ИИ нет доступа к чужим данным и инструментам с побочными эффектами.
- В модель уходит минимум персональных данных (маскирование ФИО, паспортных данных, телефонов там, где они не нужны для ответа).

**Данные и инфраструктура:**
- Шифрование: TLS везде, шифрование диска/бэкапов, чувствительные поля карточек (паспорт и т.п.) шифруются на уровне приложения.
- Секреты: не в репозитории; локально `.env` + `.env.example`, в проде менеджер секретов.
- Минимальные права: отдельные роли БД для api/worker/миграций, закрытые порты, приватная сеть между сервисами.
- Бэкапы: автоматические, шифрованные, тест восстановления.
- Логи без паролей, токенов и содержимого документов.
- Зависимости: `govulncheck`, `npm audit`/Dependabot, сканирование образов (Trivy), SAST (gosec/CodeQL), проверка секретов (gitleaks) в CI.
- 152-ФЗ: хранение ПДн россиян на серверах в РФ, уведомление Роскомнадзора, политика, согласия, процедура удаления данных.
- План реагирования на инциденты и аудит-лог действий пользователя.

## 6. Что учесть уже сейчас, чтобы не переделывать
- Все ID: UUID/ULID, не последовательные.
- Время в UTC, миграции версионируются, конфиг только через переменные окружения (12-factor).
- Идемпотентные задачи очереди; ключи идемпотентности для рендера.
- Корректное завершение (graceful shutdown) и `/healthz`, `/readyz` во всех сервисах.
- Тарифы/лимиты: таблицы `plans`, `usage_counters` с первого дня (бесплатно = один план без платежей).
- Структурные JSON-логи, trace-id сквозной.
